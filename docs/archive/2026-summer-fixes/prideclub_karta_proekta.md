## 0. Что это за продукт

Платный Telegram-маркетплейс привычек: закрытые клубы (планка, ранний подъём,
чтение, отказ от курения и т.д.), где участники ежедневно подтверждают
выполнение видео-кружком. Пропуск — денежный штраф в общий призовой фонд
клуба. В конце сезона фонд делится между лидерами (топ-N по метрике).

Механика — гибрид commitment device (штрафы за нарушение обещаний) +
социальный контроль (можно "поймать" нарушителя и получить бонус) +
геймификация (персонаж, характеристики, статусы, лидерборды).

## 1. Core Habit Loop (ядро механики)

**Статус: спроектировано полностью, реализация частичная**

Цикл участника: вступил в клуб → заплатил вход/депозит → ежедневно делает
check-in с доказательством → при пропуске получает штраф в общий фонд →
в конце сезона топ участников получает призы.

Ключевые решённые вопросы:
- Check-in ≠ просто кнопка "сделал" — обязательно доказательство (видео-кружок,
  фото, скриншот), иначе механика дисциплины ломается.
- Catch-window: другой участник может "поймать" нарушителя за деньги/бонус,
  если тот не отчитался в срок.
- Membership lifecycle: join → active → paused (депозит закончился) → left.
- Выход из клуба не удаляет историю участника.

**Не закрыто до конца:**
- Полный сценарий всех edge-cases (пустой призовой фонд за сезон, повторный вход,
  бан за фрод) — частично решено, но не всё формализовано в API-контрактах.

## 2. Финансовая механика (штрафы и призы)

**Статус: логика решена, часть уже в коде (частично)**

| Параметр | Решение |
|---|---|
| Вход в клуб | 1000 ₽ (не 1000/1000 — слишком высокий барьер) |
| Штраф за пропуск | 250 ₽ (баланс между "больно" и "не критично") |
| Депозит | 750–1000 ₽ минимум на счету для участия |
| Призовые места | 5 мест вместо 3 — выше вовлечённость, реалистичнее для старта |
| Пустой призовой фонд (сезон без штрафов) | Заранее прописанный сценарий: заменить деньги статусными бонусами или перенести в след. сезон — не провал механики, а маркетинговый кейс |
| Налоги | Не собираем паспорт/ИНН на входе. Необлагаемый лимит 4000₽/год на человека. Свыше — ответственность самого участника (прописывается в оферте) |
| Выплаты | Lava.top или Tribute как посредник, без открытия ИП на старте |

Технически часть этого уже в БД: `penalties`, `transactions`, `season_prize_rules`,
`daily_streak_snapshots`, `bonus_rules`, `suspicious_pairs` — таблицы спроектированы
и частично в миграциях (см. раздел 6).

## 3. Growth / выход на рынок

**Статус: чек-листы готовы, не запущено**

- **Партнёрка с лидерами сообществ**: бесплатный доступ основателям малых
  сообществ в обмен на приведение своей аудитории — решает cold start,
  отсутствие кейсов и статистическую достоверность одновременно.
- Готов 5-частный чек-лист: почему подход работает → 8 шагов от подготовки
  до запуска первой волны → 5 шаблонов сообщений (лидеру, follow-up, анонс,
  участникам, поддержка капитана) → анкета фильтрации участников → метрики
  успеха волны (конверсия, % чек-инов, retention).
- **Поиск партнёров в Instagram** — отдельная методика прямого поиска.
- **Реферальная программа**: 30% lifetime revenue share для партнёров/криэйторов,
  нужен кабинет партнёра (MVP описан отдельно).
- **Кабинет партнёра MVP** — минимальный функционал для старта: трекинг
  рефералов, статус выплат, базовая аналитика.

**Не закрыто:**
- Сама реализация кабинета партнёра, реферальных ссылок и биллинга revenue share
  в коде — только описание MVP.
- Не запущена первая волна через лидеров сообществ.

## 4. Персонаж и характеристики (Фаза B)

**Статус: ТЗ v3.1 готово и синхронизировано с кодом, реализация НЕ начата**

Геймификационный слой поверх денежной модели: за каждый успешный чек-ин растёт
характеристика клуба (условные очки, НЕ рубли), за штраф — падает. Сумма всех
характеристик пользователя определяет глобальный статус (Новичок → Практик →
Мастер → Легенда).

**Уже сделано (админский флоу клубов):**
- Таблица `habits` расширена 8 полями (stat_name, stat_icon, stat_gain_per_checkin,
  stat_loss_per_miss, member_limit, curator_id, photo_url, telegram_invite_link,
  archived_at) — задеплоено на прод.
- Отдельный admin-бот + Mini App (admin.prideclub.fun), owner-only авторизация.
- CRUD клубов: создание (всегда is_active=false), активация, soft-delete (archive/
  restore), permanent delete для пустых клубов.
- Заморозка финансовых полей (price/penalty) после первого вступления участника.

**НЕ сделано (собственно Фаза B):**
- Таблицы `user_stats` и `user_statuses` (статусы-справочник).
- Инкремент характеристики при чек-ине / декремент при штрафе в сервисах.
- Worker заморозки характеристики после 30 дней неактивности.
- Эндпоинты `GET /character/me` и `GET /leaderboard/stat`.
- Весь фронтенд (страница персонажа, level-up toast, таб лидерборда).

**Важное архитектурное правило:** пауза членства (`membership.status=paused`,
про деньги) и заморозка характеристики (`user_stats.is_frozen`, про очки) —
два НЕЗАВИСИМЫХ механизма, нельзя путать в логике и в БД.

**Открытый вопрос:** статусы считаются глобально по сумме характеристик всех
клубов — риск "фарма" лёгких клубов ради статуса. Требует решения до реализации.

## 5. Инженерная база / production readiness

**Статус: 6 раундов ревью пройдено, основа готова**

Хронология: `01_initial_review` → `06_dorabotki_v6` — итеративное закрытие
найденных проблем в архитектуре, безопасности и race conditions.

Закрыто:
- Service-to-service авторизация между Bot/Worker/Backend через
  короткоживущие JWT с issuer/audience claims + leeway на clock skew.
- Race conditions в PenaltyService/BonusService через `SELECT ... FOR UPDATE`
  и идемпотентные UNIQUE-индексы (`uq_penalty_per_day_reason`).
- Anti-fraud: `suspicious_pairs` для обнаружения сговора "ловец-нарушитель".
- Сезонные призы: `season_prize_rules` + JSONB snapshot в `seasons`, чтобы
  правила сезона не менялись задним числом после старта.
- Bonus points перенесены на уровень user (BIGINT), cron для протухания.
- Backup: pg_dump → age-шифрование → Selectel S3, heartbeat-мониторинг,
  retention 7 daily/4 weekly/12 monthly, RPO 24ч/RTO 4ч.
- ФЗ-152: минимизация PII, эндпоинт удаления данных, анонимизация вместо
  hard delete транзакционных записей.
- Health/readiness эндпоинты с таймаутами проверки DB/Redis.

Остаточный backlog (не блокирует MVP, но нужен для масштабирования):
- Rate limiting middleware.
- Полноценный RUNBOOK.md.
- Prometheus-метрики (auth failures/success).
- Smoke-тесты перед релизом.

## 6. Технический стек и структура (зафиксировано)

- **Backend**: Python / FastAPI
- **Bot Gateway**: aiogram (основной бот) + отдельный admin-бот
- **Worker**: Celery
- **Frontend**: React + TypeScript (Telegram Mini App)
- **БД**: PostgreSQL 14+, Redis (кэш/очереди)
- **Инфра**: Docker Compose, VPS (Selectel), nginx + Let's Encrypt
- **Оплата**: Lava.top / Tribute

Порядок разработки MVP и структура репозитория (`apps/frontend`, `apps/backend`,
`apps/bot`, `apps/worker`, `packages/shared`, `infra/`, `docs/`) уже определены
